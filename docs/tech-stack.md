## 4. Payments: why we write it ourselves

Razorpay is the gateway — India, UPI, netbanking, cards, wallets. That part is not controversial.

What is controversial is *how*. Two community Medusa v2 plugins exist, and **neither is stable**:

| Plugin | Latest | Published | Licence |
|---|---|---|---|
| `@devx-commerce/razorpay` | `6.0.0-beta.0` | — | MIT |
| `medusa-plugin-razorpay-v2` | `0.1.4` | 2025-12-31 | MIT |

A beta and a pre-1.0, both community-maintained, on the component where failure is least
recoverable and least debuggable. Under a solo-maintainability criterion — no CI, no staging, no
second reviewer — taking a dependency there is the wrong trade. **We write the provider against
Medusa's documented payment-provider interface and own it.**

More work up front. The cheaper mistake. A bounded module we understand beats an outage in someone
else's beta at 2am.

The plugins remain useful as *reference implementations*. Read them; do not depend on them.

### 7.1 Why Redis is self-hosted, and the caveat that goes with it

Co-located with Medusa: Redis is called constantly, so the round trip should be a loopback and not a
network hop. No extra vendor, no extra bill, and ADR-0002 already rules that **Redis is authoritative
for nothing** — so managed Redis would be buying durability guarantees this design says it does not
need.

**The caveat is real.** Medusa's docs say only that the Redis Workflow Engine Module *"uses Redis to
track workflow executions and handle their subscribers"*, and neither the documentation nor a search
establishes whether that execution state is also persisted to PostgreSQL. If it is Redis-only, then
Redis **is** partially authoritative and ADR-0002's test does not hold as written. Until that is
settled: enable AOF persistence, so losing the process does not lose in-flight workflow state.
Recorded as R-38.

### 7.2 The open row that blocks the others

Medusa runs **two persistent Node processes** — a server and a separate worker handling scheduled
jobs, workflow execution and event subscribers. Vercel's functions are request-scoped and cap at 300
seconds (800 with Fluid Compute), so the worker cannot live there. Supabase does not run application
processes at all.

With Postgres now fixed to **Supabase Mumbai**, the Medusa host should sit in Mumbai to keep queries
on a short hop — a page render issuing ten queries pays the distance ten times. That reshapes the
earlier recommendation: DigitalOcean's Bangalore region was chosen partly *because* it offered
managed Postgres in-region, and that argument is now spent.

Candidates worth costing, all Mumbai: **AWS Lightsail** (`ap-south-1`, billed in INR through AISPL
with a proper GST invoice), **Azure App Service** (West India, runs persistent Node, enterprise-
familiar), or a plain VPS.

**Update, 17 August 2026 — Vercel confirmed for the storefront; this row stayed open.** Sayon
confirmed Vercel for deployment. That closes the storefront row cleanly: Next.js on Vercel `bom1` is
the first-party path and the storefront is stateless.

**It cannot close this row.** Medusa's worker is a process that runs continuously — scheduled jobs,
workflow execution, event subscribers — waiting for things to happen. Vercel's model is the inverse:
a function wakes on a request, does one unit of work, and dies. This is verified, not assumed:
Vercel's ceiling is 300 seconds by default and 800 with Fluid Compute, and its own guidance is to
push work that outlives a response onto an external worker.

So the deployment is **split by construction**, and that is normal rather than a compromise:

| Piece | Where |
|---|---|
| Storefront (Next.js) | **Vercel**, `bom1` — decided |
| Medusa server + worker | **Open** — needs a host that runs always-on Node |
| PostgreSQL | **Supabase**, ~~Mumbai~~ **Sydney `ap-southeast-2`** — decided; region amended 5 Sep 2026 by ADR-0009 |
| Redis | Alongside Medusa — this document's call |

The only way Vercel hosts *everything* is to stop using Medusa, which would supersede ADR-0001 and
discard R-30's finding that Inventory Kits already model §32's six-component Ritual Set natively.
That is a real option, but it is a much larger decision than a hosting choice and must not be made by
implication.
